# B3 - Compare direct Linux, VM and container deployments

The benchmark uses the same synthetic Flask application and CPU-cost `/simulate/login` route, starts it directly on the Ubuntu runner, runs it in the built Docker image and boots the same source on an Ubuntu cloud VM in QEMU/KVM. `/health` remains a cheap readiness endpoint. `ab` generates 2,000 login-simulation requests at concurrency 25 per mode after readiness. The runner records startup time, RSS, RPS, latency, image/VM footprint and virtualization mode. The deterministic 10,000-round PBKDF2 work uses no credentials and approximates a small CPU-bound login check. Results are controlled-run comparisons, not a campus portal capacity guarantee: the guest is nested/emulated on a cloud CI VM and the short request mix does not include database contention, TLS, think time or a flash-crowd distribution.

The Kubernetes test uses a 3-node kind cluster. It applies the 3-replica manifest, checks three Ready pods, deletes one and waits for Deployment replacement, then runs a load generator while scaling to 6 replicas. The manifest uses ClusterIP because kind has no cloud load-balancer controller; the Part A/cloud manifest keeps LoadBalancer. `TaskB4/additional-service.yaml` adds the LMS with its own limits. For the production trade-off, bare metal has the fewest layers but weakest process isolation and no automated rescheduling; a VM isolates its own kernel but costs RAM/boot; containers are fastest/densest but share the host kernel; Kubernetes adds rollout/self-healing and multi-node scheduling with control-plane/operations cost.
